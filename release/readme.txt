What is this?
-----------------------------------------------------------------
	This is a simplistic 3D engine that I've been developing
	on and off for a while now in C. 

	What you're looking at is obviously a work-in-progress.

	OSLauncherSDL2 - SDL2 input, windowing and other OS tasks
	OSEngine       - The engine itself, Yin
	OSCore         - Foundational systems shared between everything
	pkgman         - Used to generate .pkg files (most files are automatically compressed)
	qmap2world     - Converts a .map file (exported from J.A.C.K.) to Yin's .wld format

What can I do with it?
-----------------------------------------------------------------
	Currently, not much. You could use J.A.C.K. to export some
	of your own maps and convert them, but right now you will
	have mixed results until Yin's editor is finished.

	I don't currently have plans to make the source code for
	the engine available, however I do plan on supporting Lua
	for scripting - when that arrives you will be able to do
	lots more!

Instructions
-----------------------------------------------------------------

Creating materials
	Materials are created as plain-ascii .mat files and are
	typically expected to be under the 'materials' directory.

	Every material must start with 'material' on the first
	line and 'end' before the end of the file.

	pass
		This specifies the shader program to be used by
		the material program and also outlines a render
		pass.
	blend <src> <dst>
		Specifies the blending mode to be used for the
		current pass. *Must* be proceeded by a valid
		'pass' command.
	var <type> <parm_name> <value>
		This specifies the value to assign to a parameter
		either exposed by the engine or by the shader
		program.

		Type can be any of the following:
			float
			int
			uint
			bool
			double
			vec2
			vec3
			vec4
			string
			texture
			builtin

		An example of usage:
			var texture diffuseMap materials/blah/blah.png
	end
		This tells the parser that it's reached the end.
		Anything following this will be ignored.

Adding new shader programs
	Shader programs require a plain-ascii .prg file, and
	may also require a .frag and .vert file, depending on
	what you're adding.

	Any PRG files *must* be placed under the 'materials/shaders/'
	path, otherwise they will not be cached by the engine.

	The PRG files are pretty basic.

	program <program_name>
		This outlines the begining of the program and
		the name it will be allocated.
	vertex <path>
		The path to use for the vertex shader.
	fragment <path>
		The path to use for the fragment shader.
	end
		This tells the parser that it's reached the end.
		Anything following this will be ignored.

	Any uniforms exposed by the shaders will automatically
	be collected by the engine and exposed to materials, including
	their default values.

Using qmap2world
	This is a pretty simple command-line tool and can
	be used like so. It's useful for quickly prototyping
	levels until Yin's editor is in a better state.
		
	qmap2world.exe -map <map_path> -out <wld_path>

	For example...
	qmap2world.exe -map worlds/convert/home.map -out worlds/home.wld

Using pkgman
	The pkgman tool needs to be pointed to a simple
	script in order for it to work. A few examples
	are provided under the 'develop' directory.

	;
		Semi-colons will be ignored, useful for
		adding comments.
	output <path>
		This specifies where the package will be
		created and what filename to use. e.g.
		'output base.pkg'
	add <path>
		Adds the specified file to the package.
	dir <path> <extension>
		This will add all files with the extension 
		provided found under the specified directory.

Technical
-----------------------------------------------------------------

PRG
	Shader program files.

MAT
	Material files.

PKG
	These are packages generated by the pkgman tool. They're
	pretty simplistic and utilise Deflate compression provided
	by the miniz library.

WLD
	Levels in Yin or "worlds" as they're referred to are
	hierarchical, every brush can have a child entity/brush and
	every entity could have a child entity/brush - there
	are no limitations (hell you could have an entire sector as a 
	child to an entity).

	Everything is then transformed in relation to the
	transform of it's parent. This allows you to have rooms
	that can be rotated with the player being rotated within
	and other crazy situations.

	There are a collection of head nodes which could be
	interpreted as sectors/rooms - the player will need
	to spawn within one of these in order to actually be
	able to navigate the world otherwise the engine will
	not be able to determine where they are.

	It's worth mentioning that every single room has it's
	own local space as well that everything is relative to.
